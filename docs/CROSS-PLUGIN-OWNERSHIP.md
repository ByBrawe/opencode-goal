# Cross-plugin prompt ownership

OpenCode Goal can share a session with other plugins, but only one component should own autonomous prompt continuation at a time.

## Contract

When a dedicated Goal is active:

1. Goal owns autonomous continuation for that session.
2. A companion scheduler such as OpenCode Loop should reject a prompt-producing loop unless overlap was explicitly requested.
3. A slash command handled by another plugin is **command-owned traffic**, not foreground human Goal steering.
4. Real user chat remains foreground steering and may preempt the current Goal turn and update its execution context.
5. A foreign command must never replace the Goal's persisted `execution.agent`, `execution.model`, or `execution.variant` merely because the command uses a local command agent.

This separates two different questions:

- **Should the other plugin start autonomous work?** The companion plugin decides this. Loop 0.5.35, for example, emits `goal-overlap-blocked` and does not persist a prompt job while a dedicated Goal owns the same session.
- **How should Goal classify the slash-command bridge produced by the host?** Goal treats a verified foreign-command bridge as command-owned traffic and does not pass it through foreground steering logic.

## OpenCode 1.18.x command bridge edge case

On current OpenCode 1.18.x hosts, submitting another slash command while a Goal provider request is still waiting for its first response byte can cancel that in-flight request even when the companion plugin ultimately rejects the command's autonomous work. The host may then materialize the command template as a local-agent model turn.

Without an ownership guard this creates a bad sequence:

```text
Goal(build) -> provider request pending
/loop devam et
Loop -> goal-overlap-blocked
OpenCode -> cancels pending Goal request
OpenCode -> command bridge under opencode-loop-local
Goal -> mistakes bridge for human steering
Goal execution -> opencode-loop-local   # wrong
```

Goal protects this boundary with a one-time per-command ownership marker. The marker is generated by the Goal plugin, attached only while an unfinished Goal exists, consumed before the core `chat.message` steering handler, and stripped before provider dispatch. A fabricated or expired marker is not trusted and remains normal foreground chat.

The marker is an internal correlation mechanism, not authorization supplied by prompt text.

## Safe outcomes

Hosts can safely take either path:

### Host honors command suppression

```text
Goal request remains active
foreign command is handled locally
no bridge model turn
Goal execution unchanged
```

### Host cancels and materializes a compatibility bridge

```text
Goal request cancelled
foreign command bridge runs
Goal ignores the bridge for steering/executor selection
session returns idle
Goal resumes exactly as Goal(build)
```

In both cases:

- no second autonomous Loop prompt is allowed by default;
- Goal remains active unless another Goal safety rule stops it;
- private ownership markers must never reach the model/provider;
- normal human chat still uses the existing steering/preemption path.

## Regression coverage

The repository keeps three layers of evidence:

- unit tests for foreign-command correlation, executor preservation, spoof resistance, and unchanged human steering;
- normal real-host steering tests to prove this guard does not weaken intentional user steering;
- a dedicated real-host Loop coexistence canary using released `@bybrawe/opencode-loop@0.5.35` on Ubuntu and Windows, including a first-token-delayed provider case that reproduces the OpenCode 1.18.x cancellation edge.

When changing command, steering, session-idle, or companion-plugin integration code, keep these ownership invariants intact rather than solving the collision by enabling two continuation owners.
